Model specification

Choose deterministic utility terms. Expected payment is the price variable; fixed effects absorb average preferences for count bins, plans, and calendar season.

Product trip-count bins

Use single counts, ranges, or an open-ended final bin. Examples: 01, 09-12, 21+. Bins must be ordered, non-overlapping, contiguous from 1, and end with a + bin.

Kernel conditioning

The kernel is the empirical basket pool used to compute expected product payment and expected trips. A basket is one positive user-month. Min support is the number of historical baskets required before using a kernel source without broadening it. Count bin is locked because it defines the product; relaxation controls what is broadened first when support is low.

Mobility Plans


Select one or more mobility plan. Each selected mobility plan is estimated and forecast separately, using the same model parameters, and all results are shown together.

Market size

Future market size is forecast from the training data. For each future month, the dashboard uses the average number of in-market users from the same calendar month in training, then multiplies it by the future market size multiplier. If that calendar month is not present in training, it uses the overall training average.

This model is still in development and should be used with caution. Use optimized pricing results as directional information, not specific recommendations.


The optimization maximizes predicted user-payment revenue subject to a predicted trip-volume constraint. Maximum trip-volume drop is the largest allowed decrease in total predicted trips relative to baseline pricing over the forecast horizon. If the monthly constraint is checked, the same limit is enforced separately in each forecast month. Evaluations per seed controls the direct-search budget for each random start; more evaluations and more seeds explore more prices but take longer. Keeping time rates proportional ties per-minute, per-hour, and per-day rates for each selected plan to a common multiplier. SciPy polish, when available, uses an open-source SLSQP local solver after direct search.
